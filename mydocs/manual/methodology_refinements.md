# 방법론 다듬기 (Methodology Refinements)

본 문서는 본가 [CLAUDE.md](../../CLAUDE.md)의 하이퍼-워터폴 절차를 fork에서 따르며 발견한 **공백·암묵 단계·잠재적 개선점**을 누적한다. 절차 자체를 평가·일반화하여 다른 프로젝트에 적용할 때 참조하기 위함.

> **운영 원칙**
> - 본가 [CLAUDE.md](../../CLAUDE.md) 본문은 수정하지 않는다 (upstream 동기화 충돌 방지).
> - 공백·개선점이 발견되면 본 문서에 항목을 추가한다.
> - 본 fork에서는 본 문서의 개선안도 본가 절차와 함께 적용한다.

각 항목은 다음 구조를 가진다.

- **상황**: 본가 절차의 어느 부분에서 발견했는가
- **공백/문제**: 절차가 다루지 않거나 모호한 부분
- **개선안**: 명시적으로 어떻게 다룰지
- **적용 시점**: fork에서 언제부터 적용

## R-001. 이슈 등록 미니 사이클

### 상황

본가 [CLAUDE.md](../../CLAUDE.md) "타스크 진행 절차" 1단계:

> "GitHub Issue에 타스크 등록 → 작업지시자가 지정한 타스크 수행"

### 공백 / 문제

한 줄로 적혀 있지만 실제 작업에는 다음이 모두 포함된다.

- 제목 결정
- 본문 구조화 (배경 / 범위(포함·미포함) / 종료 조건)
- 마일스톤 결정 및 **사전 생성** (없을 경우 `gh api repos/.../milestones` 호출)
- 라벨 결정 (선택)

또한 이슈 등록은 **GitHub에 publish되는 외부 가시 행위**라 본질적으로 작업지시자의 명시 승인이 필요하다. 그러나 본가 절차에는 이 승인 게이트가 명시되어 있지 않다.

### 개선안 — 명시적 미니 사이클

이슈 등록을 다음 3단계 미니 사이클로 분해한다.

```
(a) 초안 제시  →  (b) 승인  →  (c) 등록 실행
```

| 단계 | 수행자 | 내용 |
|------|--------|------|
| **(a) 초안 제시** | 클로드 | 제목 / 본문 / 마일스톤 / 라벨 초안 제시. 마일스톤이 없으면 사전 생성 명령도 함께 명시. |
| **(b) 승인** | 작업지시자 | "승인" / "수정 후 재제시" / "거부" 중 하나로 응답. 승인 없이 (c)로 진행 금지. |
| **(c) 등록 실행** | 클로드 | `gh api`(마일스톤 생성, 필요 시) + `gh issue create`(이슈 등록) 실행. 발급된 이슈 번호 즉시 보고. |

### 본문 표준 구조 (제안)

```markdown
## 배경
<왜 이 작업이 필요한가, 어떤 흐름의 어느 단계인가>

## 범위
**포함**
- ...

**미포함** (후속 이슈에서 처리)
- ...

## 종료 조건
- [ ] <검증 가능한 종료 기준 1>
- [ ] <검증 가능한 종료 기준 2>
- [ ] 수행계획서 / 구현계획서 / 단계별 보고서 / 최종 보고서 작성 완료
```

### 적용 시점

본 fork 작업부터 즉시 적용. R-001 자체가 첫 적용 사례 (Issue #1: NestJS agent-server 스켈레톤).

## R-002. Fork 셋업 사전 단계 (placeholder)

### 상황

본가 [CLAUDE.md](../../CLAUDE.md) "타스크 진행 절차"는 1단계가 "GitHub Issue 등록" 부터 시작.

### 공백 / 문제

저장소·리모트·로컬 도구 셋업이 갖춰진 상태를 전제. 실제 fork 시작이나 신규 프로젝트에서는 다음의 셋업 작업이 매번 발생한다.

- Fork 생성 (`gh repo fork`)
- 로컬 클론 + upstream 리모트 등록
- Issues 활성화 (fork 기본값 비활성)
- 브랜치 정렬 (devel, local/devel)
- 빌드 도구 설치 (rustup 등) + 빌드 검증
- 개인 스크립트·`.gitignore` 조정 (선택)

이 작업들이 절차 외부에 흩어져 있어 fork·신규 프로젝트마다 즉흥적으로 진행된다.

### 개선안 — 단계 0: 저장소·로컬 환경 셋업 체크리스트 (초안)

본 절은 추후 fork·신규 프로젝트 경험을 1~2회 더 거친 뒤 정식화한다. 잠정 체크리스트:

- [ ] Fork 생성 + Issues 활성화
- [ ] 로컬 클론 + upstream 리모트 등록
- [ ] 본가 브랜치 모델 정렬 (devel, local/devel)
- [ ] 빌드 도구 설치 및 `cargo build` / `cargo test --lib` 검증
- [ ] 동기화 스크립트 배치 (예: `scripts/local/sync-upstream.sh`)
- [ ] git user.email 정합성 확인 (GitHub contribution graph 매칭)

### 적용 시점

본 fork 셋업 회고를 통해 R-002를 완성한 뒤 차기 프로젝트부터 적용.

## R-007. 계획 단계 도구 버전은 *고정*이 아닌 *제약*으로

### 상황

수행계획서 §4 외부 의존성 / 구현계획서 도구 버전 명시 시점.

### 공백 / 문제

본 task 에서 `Node 20.x LTS`, `NestJS 10.x` 같이 *특정 버전*을 명시했으나 실제 진행 시 사용자 환경(Node 22) 과 도구 채널(NestJS 11 stable) 모두 달라 deviation 2건 발생. 둘 다 기능적 영향 없는 단순 버전 시차. 절차 결함이 아니라 *계획의 해상도가 너무 높았던 것*이 원인.

### 개선안

| Before | After |
|--------|-------|
| `Node.js 20.x LTS` | `Node.js 20+ LTS 또는 안정 버전` |
| `NestJS 10.x 안정` | `NestJS 안정 채널 (`@latest`)` |
| `이미지 크기 200MB 이하` | `이미지 크기 250MB 이하 (목표 200MB, 첫 실측 후 보정)` |

원칙: **계획 단계의 도구 버전은 *기능 호환 제약*으로 표현하고, 정확한 버전은 첫 실행 시 측정·기록**한다.

### 적용 시점

차기 task (이슈 #2 이후) 부터.

## R-008. 자동 검증 가능 항목은 자동화 우선

### 상황

각 stage 종료 체크 정의 시점.

### 공백 / 문제

종료 체크가 *작업지시자가 manual 명령으로 확인* 형태로 적히면 (a) 명령 차이로 인한 비결정성, (b) 작업지시자 시간 소모, (c) 회귀 보호 없음. 본 task 에서 e2e 테스트(`npm run test:e2e`)로 health 응답을 자동 검증한 경우 위 3 문제 모두 해소됨.

### 개선안

종료 체크 항목을 다음 분류로 정리:

| 분류 | 예시 | 표현 |
|------|------|------|
| **자동 가능** | API 응답, 빌드 결과, 단위 동작 | 자동 테스트 / CI 명령 (`npm run test:e2e` 등) |
| **자동 곤란** | 컨테이너 동거, restart 정책 | 명령 + 기대 출력 (사용자가 1회 실행) |
| **수동 검수** | UI 시각 확인 | 명시적 manual 표시 |

원칙: **자동 가능 영역은 자동 테스트로 종료 체크 작성**. 자동 테스트 자체가 산출물의 일부.

### 적용 시점

차기 task 부터. 본 task 에서 e2e 테스트가 효과 입증.

## R-009. 환경 의존적 / 수치형 제약은 기준치 + 허용 오차

### 상황

이미지 크기, restart 정책 동작, 빌드 시간 등 *환경/도구에 따라 변동 가능한 제약*을 종료 체크에 명시할 때.

### 공백 / 문제

본 task 에서:
- `이미지 크기 200MB 이하` → 실측 255MB, deviation 발생
- `restart 정책 자동 작동` → Docker 29 환경에서 `docker kill` 시 미발동, deviation 발생

둘 다 *경험적 추정 또는 환경 의존*에서 비롯. 종료 체크 자체가 환경마다 다른 결과를 낼 수 있는데 *단일 결정값*으로 적힌 것이 문제.

### 개선안

수치형 / 환경 의존 제약은 다음 형식으로 작성:

```
- 이미지 크기: 200MB ± 20% (실측 250MB 까지 허용, 초과 시 sub-task 분리)
- restart 정책: docker compose start 로 즉시 재기동 가능 (자동 재시작은 환경 매트릭스로 분리)
```

원칙: **단일 결정값보다 *기준치 + 허용 오차 + 한계 초과 시 후속 액션* 으로 구체화**. 이러면 deviation 이 발생해도 *계획 안의 정상 범위* 또는 *분리 가능한 후속 task*로 명확히 분류 가능.

### 적용 시점

차기 task 부터.

## R-010. 외부 정보 조회 단계의 명시화

### 상황

수행계획서 §6 의 결정사항 중 *외부 docs / API / 사용자 응답*을 조회해야 하는 항목이 있을 때.

### 공백 / 문제

본가 절차에 *진행 중 외부 정보 조회* 단계가 명시되지 않음. task #2 에서 R-2 (OPENAI_MODEL 기본값) 가 외부 OpenAI docs 조회 의존이었으나 자동화 차단(403)으로 진행 중단 우려가 발생. 작업지시자에게 1줄 응답 받아 fallback.

### 개선안

수행계획서의 결정사항 중 외부 정보 의존인 것은 다음을 명시:

- **조회 대상**: 어디서 (URL / 사람 / DB)
- **조회 시점**: 어느 단계 시작 시
- **결정 기준**: 무엇을 보고 결정하는가
- **fallback 경로**: 조회 실패 시 (네트워크 차단·docs 폐기 등) 어떻게 진행

### 적용 시점

차기 task 부터.

## R-011. 누적 환경 정합성 점검

### 상황

새 task 시작 시 *이전 task 의 산출물 (working tree, .env, 캐시 등)* 이 본 task 환경에 존재.

### 공백 / 문제

본가 절차의 "단계 0: 사전 점검" 같은 명시 단계가 없어, 이전 task 잔재가 새 task 의 자동 테스트나 빌드에서 *예상 못한 경합* 을 만들 수 있음.

task #2 Stage 1 에서 #1 Stage 3 의 .env 사본이 ConfigModule 검증 e2e 와 경합 → setup-env.ts + ignoreEnvFile 분기로 해결. 사전 점검이 있었으면 빨리 발견 가능.

### 개선안

수행계획서 §3 (영향 범위) 또는 §6 (리스크) 에 다음 항목 명시:

- **누적 환경 점검 체크리스트**:
  - working tree 가 깨끗한가 (uncommitted 변경 없음)
  - .env / .env.* 의 현재 값이 본 task 가정과 일치하는가
  - node_modules / dist / docker image 캐시가 stale 하지 않은가
  - 테스트 환경 변수가 production 과 격리되어 있는가

### 적용 시점

차기 task (#3) 부터 *수행계획서 표준 항목*에 포함.

## R-012. jest manual mock 의 단일 진실 원천

### 상황

NestJS CLI default 의 jest 설정이 *단위 테스트 (`rootDir: src`)* 와 *e2e 테스트 (`rootDir: .` = test)* 를 분리. 두 설정이 각자의 `__mocks__/` 에서 manual mock 검색.

### 공백 / 문제

`openai` 같은 node 모듈을 모킹할 때 *src/__mocks__/openai.ts + test/__mocks__/openai.ts* 가 dup 됨. 모킹 대상이 늘어날수록 dup 가 누적, 한쪽 수정 누락 시 양쪽 일관성 깨짐.

### 개선안

다음 중 1개 도입 (별도 *테스트 인프라 정리 task* 후보):

- 옵션 A: 단일 jest config 의 `roots` 를 양쪽 디렉터리로 설정 + testRegex 분기로 단위/e2e 격리
- 옵션 B: 단위 테스트도 test/ 디렉터리로 이동, src/ 는 production code 만
- 옵션 C: mock 본체를 별도 helper(`test/mocks/`) 두고 양 `__mocks__/<module>.ts` 가 re-export

### 적용 시점

본 task #2 에서 dup 발생 시점에 정식화. 차기 *테스트 인프라 정리 task* (별도 이슈) 에서 옵션 채택 후 적용.

## R-013. 2단계 검증 사다리 (jest + 컨테이너)

### 상황

backend 작업의 동일 동작 (예: ConfigModule 의 환경변수 검증) 을 jest 단위/e2e 환경과 docker 컨테이너 환경에서 *모두* 검증할 때.

### 공백 / 문제

대부분의 경우 두 환경 중 하나만 검증 → 다른 환경의 정합성은 추론에 의존. 환경 차이 (NODE_ENV, .env 처리, 의존성 hoisting 등) 로 인한 *production-only* deviation 발생 가능.

task #2 의 Stage 1 (jest e2e) + Stage 3 (compose 부팅) 에서 동일 ConfigModule 검증을 두 layer 에서 각각 검증 → *jest 의 가짜 환경에서 통과한 검증이 실제 컨테이너에서도 동일 동작*임을 입증.

### 개선안

backend 작업의 종료 체크에 다음 *2단계 검증 사다리*를 권장:

| 단계 | 환경 | 목적 |
|------|------|------|
| **1** | jest 단위/e2e | 빠른 회귀 검증, 모킹·격리 활용 |
| **2** | docker compose | production 환경 정합성 (NODE_ENV, .env, 의존성 hoisting) |

자동 명령으로 표현되면 R-008 (자동 테스트 우선)과 자연스럽게 결합.

### 적용 시점

차기 backend task (#3 등) 부터 *수행계획서 §2 종료 조건* 에 명시 권장.

## R-014. 이슈 등록 시 활성 다듬기 점검표 의무화

### 상황

이슈 등록 시점에 *현재 누적된 R-* 다듬기 중 본 task 에 적용할 항목*이 명시되지 않으면, 작업지시자나 클로드가 *어떤 절차 자산을 사용 중인지* 즉시 파악 어려움.

### 공백 / 문제

task #1/#2 의 이슈 본문에는 다듬기 사전 적용 명시 없음. task #3 부터 *"R-007~R-013 사전 적용 점검 표"* 를 이슈 본문에 포함하기 시작 → *어떤 다듬기가 본 task 에 어떻게 적용되는지*를 이슈 단계에서 가시화.

### 개선안

이슈 본문에 다음 표 형식 의무 포함:

```markdown
## R-* 사전 적용 점검

| ID | 본 이슈 적용 |
|----|-------------|
| R-007 | <본 task 에서의 적용 방식> |
| R-008 | <적용 방식> |
| ...   | ... |
```

활성 다듬기 (현재 정식화된 R-*) 모두 1줄씩 명시. 적용 안 함이면 그 사유를 적음.

### 적용 시점

차기 task (#4 이후) 부터 의무. task #3 의 이슈 #3 본문이 *첫 시도* — 효과가 본 task 종료 시 입증됨.

### 효과 (task #3 회고 기반)

- 작업지시자가 이슈 단계에서 *방법론 자산이 어떻게 활용될지* 즉시 파악 가능

## R-015. 수행계획서 §6 결정사항에 반대 입장 근거 명시

### 상황

수행계획서 §6 의 *각 결정사항(R-N-A/B/C 등)* 에 추천안 + 이유는 명시하지만 *반대 입장의 근거*는 제시 안 됨.

### 공백 / 문제

작업지시자가 추천을 검증할 때 *반대 입장의 근거를 자기 머리로 떠올려야* 함. 추천이 *철저하지 않을 때* 작업지시자가 검증 질문을 하지 않으면 잘못된 결정이 통과될 수 있음.

task #3 의 R-3-D 사례:
- 초안 추천: "직접 검증" (zod 보류)
- 작업지시자 검증 질문: *"zod 보류 이유?"*
- 재검토 → zod 도입의 단일 진실 원천 가치 발견 → 결정 변경

만약 초안 단계에서 *반대 입장 근거*도 함께 제시했다면, 클로드가 self-check 단계에서 양쪽을 비교하고 *처음부터 더 정확한 추천* 가능.

### 개선안

수행계획서 §6 결정사항 표준 형식:

```markdown
### R-N-X. <항목>
- **추천**: <안>
- **이유**: <근거 1~3줄>
- **반대 입장 근거**: <대안의 장점 / 추천안의 약점 1~3줄>
- **결정 경위** (필요 시): <변경 이력>
```

*반대 입장 근거*가 *추천의 정확도를 self-check 하는 장치* 역할.

### 적용 시점

차기 task 부터.

### 효과 (task #3 R-3-D 사례 기반)

- 추천 변경 시 *근거 기반 신속 결정* 가능
- 작업지시자 검증의 *직접 입력* 제공
- 추천의 *철저함 인센티브*
